## Context

Состояние энкаунтера уже хранит отдельные `entries` с уникальными instance-id, даже когда несколько entries ссылаются на один каталоговый `monster.id`. Проблема касается представления: повторные монстры визуально дублируют большие карточки целиком.

## Goals / Non-Goals

**Goals:**

- Группировать encounter entries по `monster.id` для отображения.
- Показывать одну полную карточку монстра на группу.
- В карточке отрисовывать N секций экземпляров (name + remove button), где N равно количеству entries этого `monster.id`.
- Удаление из секции должно удалять только соответствующий entry.

**Non-Goals:**

- Изменение формата URL-сериализации энкаунтера.
- Изменение правил расчета encounter difficulty/party strength.
- Объединение или дедупликация данных в store (группировка только для UI).

## Decisions

1. Группировать entries в `App` на этапе подготовки данных для рендера (например, `useMemo` с map по `monster.id`), без изменения store структуры.
2. Расширить `MonsterCard` поддержкой списка экземпляров с отдельным remove handler на каждый instance id.
3. Визуально сохранить полную информацию монстра в карточке один раз, а секции экземпляров разместить в header/верхней части карточки как компактный список.

## Risks / Trade-offs

- **[Risk]** Пользователь может потерять ощущение исходного порядка entries при смешанных дублях → **Mitigation:** секции внутри карточки показываются в порядке добавления экземпляров; удаление работает строго по конкретному instance.
- **[Risk]** Более сложные пропсы `MonsterCard` → **Mitigation:** сохранить backward-compatible API или выполнить локальный рефактор с явными типами.

## Migration Plan

Изменение только в клиентском UI. Миграция данных не требуется.
