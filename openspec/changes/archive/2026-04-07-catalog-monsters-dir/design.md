## Context

Сейчас `build-catalog.mjs` читает один файл `data/monsters.yaml` с ключом `monsters: []`. В репозитории уже есть `data/monsters/book-tier1.yaml` с тем же ключом `monsters` и массивом карточек.

## Goals / Non-Goals

**Goals:**

- Обнаруживать все файлы **`*.yaml`** непосредственно в **`data/monsters/`** (без рекурсии в подпапки, если не оговорено иначе — проще и предсказуемее).
- Для каждого файла: ожидать тот же корневой документ, что и у агрегата: **`monsters`** — массив объектов монстров.
- **Порядок merge:** отсортировать пути файлов лексикографически (например `book-tier1.yaml` до `misc.yaml`), внутри файла сохранять порядок элементов массива; итог — один массив `monsters` для валидации.
- **Дубликаты `id`:** как сейчас — ошибка с указанием конфликта (включая межфайловые дубликаты).
- Содержимое бывшего `data/monsters.yaml` перенести в новый файл под `data/monsters/` (например `seed.yaml` или по смыслу), затем удалить корневой `data/monsters.yaml` или оставить только короткий комментарий/README-ссылку — предпочтительно **удалить** после переноса, чтобы не было двух источников правды.

**Non-Goals:**

- Рекурсивный обход `data/monsters/**/*.yaml` (можно добавить позже отдельной задачей).
- Изменение формата JSON на клиенте или схемы `Monster` в TypeScript.

## Decisions

1. **Формат каждого файла** — `monsters` array (как агрегат), а не «один монстр в корне документа»: соответствует уже существующему `book-tier1.yaml` и упрощает merge.

2. **Пустая папка** или отсутствие `*.yaml` — сборка **завершается с ошибкой** с понятным сообщением (или 0 монстров — лучше **ошибка**, чтобы не деплоить пустой каталог неожиданно); зафиксировать в реализации как fail-fast.

## Risks / Trade-offs

- **[Risk]** Забыли перенести запись из старого `data/monsters.yaml` — **Mitigation:** задача в tasks и проверка diff.

## Migration Plan

Перенос записей → обновление README → правка скрипта → `npm run build`.
